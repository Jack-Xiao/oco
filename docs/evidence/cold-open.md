# 无面板时首次打开会话：黑屏与等待（Remote，2026-10-01）

用户反馈：关掉所有对话、没有面板时，第一次打开一个会话“加载一下，然后黑一下屏，然后又加载一下，然后才显示对话内容”，并且感觉久了点。基线为已部署的 `d73bf91`。

## 测量方法

- 探针 [cold-probe.mjs](cold-open/cold-probe.mjs)：本机真实 VS Code，独立配置档（`.oco-test/co`）经 Remote-SSH 连 gcp-workstation（`/home/user/ai`，托管模式，探针窗口自己的 `opencode serve`）。每次启动一个新窗口，从侧栏依次打开第 1、2、3 个会话，每次打开后执行 Close All Editors，所以每次都是新建面板。第 1 次是新窗口里的第一个面板，第 2、3 次是同一窗口里关掉再开。已装版本直接用；测试版用 `--extensionDevelopmentPath` 加载 `~/oco-perf/<版本>`，不动已安装扩展。
- 每次打开记录：
  - 窗口的 CDP 截屏流，算出编辑区每帧的平均亮度和标准差。帧图只存在本机临时目录，不入库。
  - 页面内每个动画帧的状态：骨架屏、官方 logo 闪屏、`#root` 文字长度、输入框、时间线行。
  - 页面的绘制和资源时间、桥接请求时间线。
  - 工作台侧的标签页和 webview iframe 出现时间。
- **shown** = 页面里出现该会话的时间线和输入框；**visible** = 之后第一帧画面上真有内容（标准差 ≥ 15）。阶段按帧分为 editor（VS Code 空编辑区的颜色）、dark（明显更暗的空页面）、other（骨架、闪屏等）。
- 汇总：`node cold-open/summarize.mjs <label>...`；单次时间线：`node cold-open/timeline.mjs <label> <k>`。原始数据在 `cold-open/*.json`（`now1` 的帧图文件名有覆盖错误，只用它的亮度和时间线）。

## 发现

基线一次新窗口首开（`now2` #0，共 1252 ms）的时间线：

| 时间（ms） | 画面 | 页面在做什么 |
| --- | --- | --- |
| 0–537 | VS Code 空编辑区（灰） | 126 标签页出现；140 iframe；381 文档开始；394–674 下载主包 4 MB 和 CSS；首帧要等 CSS |
| 537–852 | 黑底骨架屏 | 执行主包、桥接握手、载入应用；828 发出健康检查 |
| 852–941 | 官方 logo 闪屏 | 官方 `ConnectionGate` 等健康检查（一个往返） |
| 941–1217 | 全黑空白 | 骨架屏在 `#root` 有子节点时就被移除；会话页已挂载但还没有数据；940 发出约 25 个启动请求，消息 1155 返回 |
| 1217 | 内容 | — |

1. **黑屏、闪屏、再黑屏**：骨架屏是 `#root` 一有子节点就移除。官方页先放 logo 闪屏，之后是没有文字的空页面，所以出现“灰 → 黑骨架 → logo → 黑 → 内容”。官方深色底（rgb 8,8,8）也比 VS Code 编辑区（#1f1f1f）暗得多。
2. **新窗口首开长会话多等 1.2–1.6 s**：消息列表按页取。被截断的助手消息，其上一条用户消息不在这一页里，页面会在列表返回后逐条补取（`context/server-session.ts` `loadMessages` 的 `fetchMessage(parentID)`），补完才渲染。桥接暂缓的 `/provider` 恰好在消息列表返回时放行。服务端单线程，补取请求排在它后面：服务刚启动时 1.2–1.6 s，`ab-cold3` 里有一次约 5 s。
3. **健康检查**：只省一个往返的一部分。应用启动后本身约 100 ms 才发出消息请求，健康检查的往返（快隧道约 80 ms）与这段时间重叠。
4. **其余时间**：
   - VS Code 创建面板 150–450 ms：点击传到远端扩展再传回，新窗口第一次更慢。
   - 每个新面板都重新下载主包 4 MB 和 CSS 0.5 MB：快隧道 150–300 ms，慢隧道几秒。不同面板之间没有缓存。
   - 执行约 150 ms。
   - 消息请求 150–250 ms：服务端同时处理约 25 个启动请求。
   - 中文界面的两个语言分块（69 KB）在应用启动后才下载，与上面重叠。

## 改动

| 项 | 内容 | 位置 |
| --- | --- | --- |
| 1 | 骨架屏：<br>· 用 VS Code 编辑区底色（`--vscode-editor-background`），层级高于官方闪屏。<br>· 一直保留到 `#root` 出现文字（会话、错误页、恢复页）或输入框（新会话没有文字），最多 10 s。<br>· 官方启动健康检查在每次正常启动时也会短暂渲染“无法连接”页（`recovery.tsx` 注释），所以这个页面要持续 1.5 s 才算（与 `UNREACHABLE_MIN_MS` 一致）。<br>· 不做淡出：首个内容出来后页面可能忙 1 s 左右，过渡动画拿不到帧，曾让内容晚 1–1.7 s 才看得到（`ab-cold1/2` 的第 1 次）。<br>· `__OCO_STATS__.boot` 记录原因和时间。 | `apps/chat-webview/index.html`、`src/main.tsx` |
| 2 | 暂缓的 `/provider` 改为在页面报告已显示会话后才放行（新的 ui 动作 `painted`，骨架屏移除时发出），上限 10 s，与骨架屏超时一致。原来在第一个消息列表返回时放行 | `apps/extension/src/bridge-core.ts`、`main.tsx`、契约 |

**撤回：跳过启动健康检查**（A/B 的 `cold1`、`cold3` 带着它）。

- 做法：宿主连接状态为 `connected` 时，在页面初始化数据里带 `serverReady`，页面传 `disableHealthCheck`。
- 撤回原因：
  - 快隧道下只省 0–30 ms：应用启动后本身约 100 ms 才发消息请求，与健康检查往返重叠。
  - 有回归。服务对新连接不通、但已有事件流还在时（Remote 隧道半断），宿主仍是 `connected`，页面跳过检查门。启动请求失败后落到通用错误页，而不是“无法连接”页；服务恢复后也不会自动继续，因为 `recovery.tsx` 的自动重载依赖检查门。
- 发现来源：另一个会话的 `t010-recover initial-unreachable` 失败，以及 Grok 只读审查 [cold-open-review](cold-open-review.md) 的第二条 medium。
- 现在：logo 闪屏仍会渲染，但被骨架屏盖住。
