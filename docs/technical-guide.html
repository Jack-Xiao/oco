01 · PRODUCT BOUNDARY

oco 让 OpenCode 进入你的编辑器工作流

想象你正在 VS Code 里修一段代码：选中函数，加入聊天草稿，问 AI 为什么出错；AI 修改工作区文件后，你点一下路径，编辑器跳到那一行。oco 的主要价值，是把这些动作连接起来，减少在浏览器、终端和编辑器之间切换。

这涉及三个不同角色：VS Code 是工作台，oco 是连接工作台和对话的客户端，OpenCode Server 是实际管理会话、调用模型与执行工具的服务。模型供应商提供生成能力；服务器决定如何把生成结果、工具调用和权限流程组织成一次任务。

看到一个功能时，先问“谁真正负责它？”
用户看到的事情主要负责者oco 的工作
模型写出回答模型 + OpenCode Server传输输入并呈现返回的内容
运行工具、读取/修改代码OpenCode Server 所在环境显示工具结果和权限请求，连接编辑器查看动作

因此，升级 oco 不等于升级 OpenCode Server；打开更多聊天面板，也不应该意味着启动更多服务器。聊天页面打不开时，服务端任务可能仍在运行。

这张图里有两种不同的边界。第一种是进程/安全边界：网页不能随意调用 VS Code API，必须把意图交给宿主。第二种是网络/机器边界：宿主与服务器可能不在同一位置，通信会慢、断、失败。

“前端”通常指用户看到并交互的页面；“后端”通常指接收请求、保存数据、执行业务的服务。oco 又多了一层宿主适配器：它不是整个 AI 后端，却掌握 VS Code 能力和服务器凭据，承担网页与服务之间的可靠连接。

为什么不能把它看作一个普通网页？

普通浏览器网页常常直接向网站服务器请求数据。这里的聊天页面被放进 VS Code 的受限环境，真实服务地址和凭据留在宿主。页面发出的请求会被包装成消息，让宿主代为执行；文件链接也必须变成受控的“请在编辑器中打开”请求。

“同一个应用”为什么还要分成多个进程？

一个进程可以看成有自己内存和运行环境的程序容器。分开运行有助于隔离权限与失败，但双方不能直接拿对方的函数、流或对象来用。因此需要明确协议：发送什么、如何关联回复、什么时候作废。只理解这一点，就能理解桥、身份和恢复为何占了大量工程工作。

依据：panels.ts · bridge-host.ts · 桥契约 · 架构设计（含历史目标，不能全部当成现状）

03 · EMBEDDING EXPLAINED

“嵌入 OpenCode Web”具体嵌入了什么？

oco 把 OpenCode 的前端源码作为构建材料，将它适配、编译并随扩展一起分发，再在 VS Code Webview 内挂载官方 App。

Webview 是 VS Code 提供的自定义网页容器：HTML 决定结构，CSS 决定外观，JavaScript 决定交互。聊天这种复杂界面适合放在 Webview；简单的树形会话列表则用 VS Code 原生 TreeView。二者看起来在同一窗口，技术实现却不同。

方案实际含义对 oco 的意义
iframe 打开远端网站网页里再嵌一个网址，界面通常由远端网站提供不是当前主路线；会直接面对网站嵌入策略、认证、跨源等问题
源码嵌入官方 Web App拿固定上游源码，应用补丁并打包成本地扩展资源当前路线。能深度适配，但要维护对上游内部接口的依赖
完全自研聊天 UI自己实现消息、Markdown、权限、工具卡片和同步不在当前并行实施范围；自由度大，维护面也大

复用的是产品界面，改变的是运行环境

原来的 Web App 假定自己生活在浏览器里，可以导航、保存偏好、发网络请求、开链接、使用 Worker。进入 VS Code 后，这些习惯未必成立。oco 提供 Platform 适配，把网络请求接到桥，把存储接到宿主，把文件打开接到编辑器，同时限制原有多标签、终端和不适合嵌入的入口。

SDK 是方便前端调用 OpenCode 接口的一套代码。它知道如何组织诸如“读取会话”的请求。替换底层 fetch 可以改变运输路径，但 SDK 仍然依赖上游的数据格式：服务器把某字段改名，消息桥不会自动帮它理解新字段。

最重要的维护代价：你省下了从零造聊天 UI 的工作，却接下了“固定版本、补丁重放、服务兼容性、嵌入环境回归”的维护工作。补丁能成功应用，只证明文本还能改上去，不证明行为仍正确。

依据：App 挂载与 Platform · 打包适配 · 上游固定与补丁重放 · ADR-002

04 · FOLLOW ONE MESSAGE

从“帮我修这个函数”到回答出现在屏幕

下面是一张可点击的教学流程图，不连接模型，也不会实际发送消息。按顺序点按钮，看每一层拿到什么、做了什么。

1 · 输入先成为草稿

文字和加入的代码先留在当前会话的输入框。加入草稿不等于发送；编辑器内容之后再变化，也不会悄悄替换已经插入的文字。

编辑器选区 → 宿主插入草稿消息 → 当前会话 composer
  1. 写草稿：用户输入或从编辑器加入代码，页面保存尚未提交的内容。
  2. 构造请求：官方 App/SDK 把文本、目标会话与模型等信息组织成请求，经平台 fetch 交给桥。
  3. 宿主检查：确认消息属于当前文档和面板，路径与方法被允许，目录与会话身份匹配；再映射真实地址并附认证。
  4. 服务接受与执行：OpenCode Server 接收任务，联系模型，按权限运行工具。收到 HTTP 成功响应不等于任务已完成。
  5. 事件推动界面：服务不断产生消息/工具/状态事件，经流式桥回到页面，同步层更新状态，SolidJS 更新相关 DOM。
  6. 用户停止：必须让服务端收到停止当前会话执行的业务请求。仅关闭浏览器侧网络读取，不等于终止模型任务。

为什么“连接成功”和“模型能回复”是两件事？

健康接口能证明某服务可达，却不能证明模型凭据有效、额度充足、模型选择正确、工具权限合适。类似于你能拨通公司总机，不代表目标工作人员一定能完成工作。真正的验收需要一次有效发送、实际增量显示和任务结束证据。

为什么网络失败后不能自动重新发送？

可能服务器已经收到并开始修改文件，只是“已接收”的响应丢了。如果客户端看到超时就盲目重发，会重复执行任务。此时应先核对服务端状态；不能确定时，要明确告诉用户发送结果不确定。重连事件流可以自动重试，重发有副作用的任务需要更谨慎的语义。

依据：页面桥 · 网络核心 · 发送状态 · 传输决定

05 · TRANSPORT

消息桥：把网页请求运到正确的服务

fetch 是网页常用的请求接口：给它 URL、方法和内容，拿到一个响应。OpenCode Web 已经围绕它构建了 SDK。oco 保留这套调用习惯，却替换实际传输：网页请求 http://oco.bridge 这个虚拟源，由 bridgeFetch 转为 VS Code 消息，宿主再访问真实服务。这个名称不是需要配置 DNS 的服务器地址。

跨进程不能直接递过去一个“响应对象”

浏览器的 Response、ReadableStream 和函数不是普通 JSON 数据，不能指望在宿主与网页间原样复活。协议因此将响应拆成 fetch.head（状态和响应头）、fetch.chunk（数据块）、fetch.end（结束）或 fetch.error（失败）。页面再用流接口把它们拼回 SDK 熟悉的响应。

Web App / SDK
  fetch("http://oco.bridge/…")
        ↓ bridgeFetch
  fetch.request { requestId, generation, url, method, body }
        ↓ VS Code postMessage
  宿主：校验 → 固定真实端点 → 加认证 → HTTP
        ↑ fetch.head → fetch.chunk → fetch.chunk → fetch.end
  页面：ReadableStream → Response → SDK / UI

HTTP 是一次请求，SSE 是持续到来的事件

读取会话列表时，HTTP 响应通常返回一份 JSON 就结束。模型生成时，客户端需要持续知道“新增一段文字”“某工具开始”“任务结束”。SSE（Server-Sent Events） 是在 HTTP 连接上不断发送事件文本的方式，像保持通话的播报频道；用户发消息或点停止仍走另外的请求。

WebSocket 提供另一种双向长连接，终端交互常用它。替换 fetch 不会自动接管 WebSocket。当前 oco 不提供嵌入终端，相关入口被限制，WebSocket 构造也被拦截。不能因为聊天流式成功，就推断终端协议已实现。

事件消费者当前做法代价 / 边界
每个聊天面板官方 App 经自己的桥读取事件流多个面板意味着多份订阅和前端状态；隐藏后仍存活
原生侧栏每窗口另有 SessionFeed 在宿主读 /event，更新列表状态这是单独的流，不是聊天面板共享的中央事件总线
重复 provider 查询同一桥/文档中，对满足条件的在途 GET 合并只解决特定重复请求，不是所有请求缓存，也不是共享 SSE

背压：接收方慢下来，发送方会跟着减速吗？

“背压”可以理解为流水线后一道工序说“我处理不过来了，先别再送”。当前桥逐块向页面发送，尚未形成页面队列反向控制宿主读取速度的完整机制。网页里的流对象存在，不等于跨进程的整条链路已经有背压。

这在短对话里未必明显，但多个常驻面板、长会话、大工具输出或慢远程连接可能使内存和排队时延增加。工程上的后续选择包括有界队列、合并小事件、溢出后重拉快照；这些是改进方向，不能写成已落地能力。

取消至少有三个不同层次

  • 取消待发送：模型信息还未就绪时撤回排队发送，任务可能尚未抵达服务。
  • 取消网络：AbortSignal → fetch.abort → AbortController 停止某次 HTTP 读取；关闭面板会清理本面板请求。
  • 取消任务：官方 UI 发出业务停止请求，让 OpenCode 停止当前运行；要靠真实服务与模型验收确认，不能用网络断开代替。

依据：bridge.ts 协议 v2 · 网页流重建 · 宿主分块、取消与 provider 合并 · 侧栏事件流 · 逐项源码核对

06 · IDENTITY & LIFECYCLE

为什么一个聊天面板需要这么多“身份证”？

你先打开会话 A，随后切到 B。此时 A 的网络响应才回来。如果系统只知道“这是某个聊天窗口的回复”，旧数据可能污染 B。解决问题的关键，是区分服务身份、工作区目录、会话、面板，以及这一版网页文档。

身份回答的问题举例
connectionId正在连哪一个服务上下文？不能因为前端都用 oco.bridge，就把不同服务器的偏好和凭据混在一起
directory任务属于哪个项目目录？同一服务上两个项目的同名文件不能混淆
sessionId是哪一段长期对话？切换会话后，草稿仍应回到它原来的会话
panel / role是哪一个 VS Code 标签？主面板可以切会话；固定面板用于并排比较
docId / generation是重载前还是重载后的网页？旧网页发来的迟到消息不能影响新网页
requestId同一网页里具体是哪次请求？将某块响应数据配给正确的流

主面板与固定面板

日常点击侧栏会话，优先复用一个 main 主面板。想对比时，通过“Open in New Panel”打开 pinned 固定面板。如果目标会话已经显示在某面板，则优先聚焦它。这里的 pinned 是 oco 面板角色，不应与 VS Code 通用的“固定标签”概念混为一谈。

同连接、同目录切换会话时，宿主更新当前绑定并发 navigate，页面的内存路由随之切换；不会每次重建整个网页。跨目录则需要重建桥和文档，因为安全策略中的目录边界变了。

generation 是一张只在本次网页生命周期有效的票

新网页先发 hello，宿主退休旧连接并分配新的 generation，再发 welcome。后续消息带上这张票。旧文档的请求或响应即使迟到，也会被拒绝。这类似于你换了房间门禁卡，旧卡不能再进入新房间。

两个容易混淆的动作：切到另一个编辑器标签，只是隐藏面板；当前实现保留它的文档、内存和事件流。真正关闭面板或重载文档，才清理相应桥请求。保活换来了切换速度，也增加了常驻资源成本。

断线后怎么恢复？

侧栏先打开事件流并临时缓冲，再拉取会话/状态/权限/提问快照，最后回放缓冲的事件。这样尽量补上“拉快照期间发生变化”的窗口。失败后按退避策略重连；401 认证失败需要修复凭据，不能无止境重试。

聊天面板仍主要依赖官方 App 的同步机制；oco 的桥保证旧代作废、请求能重新建立。这不等于服务支持断点续传或完整事件重放。没有服务端游标，就不能仅凭客户端编号保证一次不漏地恢复每个中间事件。

依据：ADR-007 单主面板 · 面板注册表 · 内存路由与守卫 · 快照/事件恢复

07 · WHERE THINGS LIVE

“保存了”之前，先问保存的是哪一种状态

聊天历史、没发送的文字、页面布局和服务器密码，都叫“状态”，但它们不能存到同一个地方。否则可能出现：重开后草稿串到另一个会话、换服务器却沿用错误密码、前端缓存把真实运行状态覆盖掉。

为什么接管 localStorage？

浏览器通常按网址来源保存 localStorage。但这里网页的资源地址属于 VS Code，而业务请求又都使用虚拟源。直接沿用官方页面原先的键空间，容易把窗口、连接和草稿混在一起。oco 安装了一层存储垫片，把这些操作转成有作用域的宿主存储。

作用域就是“这份数据属于多大的范围”：全局 UI 偏好可以共享；窗口布局属于面板；连接缓存属于某服务；草稿属于会话。宿主按单个键保存，同一键串行写，减少两个面板各拿一张旧表覆盖对方新值的问题。

确认投递比“发出消息”更重要

从编辑器加入代码时，宿主先记下待插入内容。页面确认它确实插入了正确会话的草稿后，宿主才移除队列项。面板隐藏时可以延后投递。这个小小的确认机制，是防止“看起来点过按钮，但代码丢了”的关键。

SecretStorage 保护的是连接秘密的存放位置，不意味着聊天内容或草稿自动获得同等级保密能力。日志、证据文件和故障报告仍需避免保存密码、认证头、完整私人对话或图片字节。

依据：宿主存储 · localStorage 垫片 · 草稿确认与恢复 · 凭据使用 · ADR-005（面板行为由 ADR-007 修订）

08 · SERVICE OWNERSHIP

连接一个已有服务，与拥有一个子进程，责任不同

attached：连接现有服务

用户已启动 OpenCode，oco 读取地址并认证连接。服务由用户管理，扩展不能因为断线、退出或切换工作区就停止它。

适合：已经有稳定的个人/团队服务，想接入 VS Code。

managed：扩展启动服务

oco 使用配置的可执行文件启动自己的 opencode serve 子进程，监听回环地址与自动分配端口，使用本次随机密码。

适合：希望在工作区里由扩展负责启动并管理它自己的服务。

当前 managed 是每个窗口一个服务进程，多个面板共用。清理时只能向自己实际 spawn 出来的子进程发信号。端口上碰巧有一个进程，不能据此认定“这是我的”。

可执行文件、配置和模型凭据仍有前提

managed 不代表安装好扩展就自动获得完整模型环境。对应宿主机器上需要可运行的 OpenCode、正确的配置和能使用的模型。服务意外退出时会呈现退出状态，当前实现不无限自动重启；要区分“恢复客户端连接”和“重启自己管理的服务”。

Workspace Trust 为什么参与？

打开一个陌生仓库，并不意味着同意它让机器执行任何命令。VS Code 的工作区信任状态帮助扩展限制自动启动和写操作。桥策略在不受信任工作区拒绝业务写操作；它与 OpenCode 运行工具前的权限机制是两层不同的检查。

依据：managed-server.ts · connection.ts · 工作区与会话策略 · 使用说明

09 · LOCAL VS REMOTE

远程模式最重要的不是网址，而是位置

在普通本地工作区里，VS Code 界面、扩展宿主、项目文件可能都在你的 Mac 上。切到 Remote-SSH 后，界面仍在 Mac，工作区扩展宿主与项目通常在远端机器。oco 清单将扩展设为工作区类型，让网络访问与项目操作靠近远端代码。

同样写 127.0.0.1，指的可能不是同一台机器

127.0.0.1 意思是“发起连接的这台机器自己”。如果请求由远端 Extension Host 发出，它就指远端。若你在 Mac 浏览器输入同一地址，它指 Mac。桥的价值之一，正是让网页不需要直接访问远端回环地址，也不需要拿到服务器密码。

网页资源又走另一条路径：宿主用 asWebviewUri 将扩展资源转换为 Webview 可访问的 URI。资源地址用于下载 HTML/JS/CSS/Worker，业务服务地址用于会话 API；不要把两者混成一个。

图片与文件为什么特别容易出错？

Mac 剪贴板里的图片字节、远端工作区中的文件、编辑器尚未保存的文本，是三种来源。远端服务拿到 /Users/…/photo.png 这个字符串，并不意味着能读取 Mac 的图片；反过来，服务返回一个路径，也不证明本机同名路径就是它指的文件。

当前文件打开策略要求服务与宿主文件系统关系满足限制，并检查真实路径落在绑定工作区内。Remote-SSH 中宿主与服务同在远端回环地址时，打开远端文件是合理路径；任意第三方远程服务不能靠字符串映射保证安全与正确。

为什么远程首开慢，同窗口第二次却快？

首开要下载前端包、完成桥握手、检查服务、拉会话，再渲染第一屏。远程通道让大文件与多次往返更明显。oco 对远程主包做 gzip 传输与浏览器解压，使用 import map 把解压后的模块接回加载图；对部分启动请求延后，优先让聊天内容出现。

gzip 是减少传输字节的压缩；import map 是告诉浏览器“这个模块标识应去哪里加载”的映射。它们改善加载路径，却也增加了与 Vite 输出格式、相对模块路径和浏览器能力的耦合。加载器失败时有原入口回退，但仍需实际远端复验。

历史记录中已有 GCP 工作站安装、截图和部分真实操作证据；仍不能由此推断所有网络中断、图片、中文输入法、Windows 和长时运行已验收。已复制文件、已安装扩展、已 Reload Window、已完成真实操作，是四个不同证据层次。

依据：extensionKind · 压缩加载器 · 文件来源边界 · 远程安装 · 首开历史实测 · VS Code 官方：扩展宿主位置

10 · FROM CHAT TO CODE

让对话真正连上代码，需要保持来源与语义

加入选区：传内容，而不只是传路径

如果你修改了一段代码却还没保存，磁盘上的文件与编辑器中看到的不一样。加入对话时，应使用编辑器文档里的实际内容，并保留文件与范围信息。插入草稿后，它是一份明确时点的文本；不会随你的继续编辑暗中变化，也不会自动发送。

打开文件：前端提出意图，宿主决定能否执行

对话中的文件名来自模型或工具结果，应作为数据处理。宿主检查路径、目录范围、普通文件条件与服务位置，再用 VS Code API 打开。../ 穿越和符号链接都可能绕开单纯字符串前缀判断，因此实现使用真实路径检查。任意网页请求不能变成任意本地文件读取。

还有一个交互细节：自动打开文件会改变焦点。如果用户已经主动回到聊天输入框，稍晚的自动打开结果不应再次抢走焦点。正确性不仅是“文件打开了”，还包括“在合适时机打开，并尊重用户当前动作”。

Diff 是哪两个时点的差异？

Diff 展示两份内容之间的变化。Git 工作区 Diff比较 Git 基线与当前文件；单轮会话 Diff依赖那一轮前后快照；工具调用本身的变更又可能是第三种范围。三者不是同一件事。

本项目已围绕单轮 Diff 的来源与缺失情况做适配。应记住：轮次期间你或别的进程也可能修改工作区，因此差异不能无条件称为“全都是 AI 改的”。缺快照、缺 blob、非 Git 环境或某些文件类型会让差异不完整；空数组也不一定意味着没有发生修改。正确回退应告诉用户差异不可用，必要时打开文件或查看有明确来源的 Git 差异。

轨迹：用服务器已有记录解释执行过程

对话适合读答案，轨迹适合看用户输入、模型请求、工具调用、子会话、用量与时间之间的关系。当前轨迹来自同步状态里已有的服务记录，而不是 oco 偷偷记录全部模型网络原始请求。

因此可展示的“思考”只能是服务/模型实际返回并保存的内容，不能视为完整内部思考过程。推算的首 token 延迟、吞吐或费用也应与实测值区分；子智能体的卡片与子会话记录，是 OpenCode 的执行结果，不代表 oco 新造了一个 Agent 调度引擎。

链接为何曾经打开系统浏览器？

Webview 的静态资源有特殊基地址，普通网页中的相对会话链接可能被解析成一个可外开的 HTTPS 地址。仅阻止网页默认事件并不总能阻止 VS Code 的链接拦截。补丁 0016 在嵌入模式移除对应会话 href，由按钮意图经过宿主 openSession 路径切换。这说明嵌入适配要改变行为边界，不能只改 CSS 外观。

依据：C1 编辑器集成 · 路径加固 · Diff 来源 · Diff 展示 · 轨迹 · 链接修复证据

11 · FRONTEND WITHOUT THE JARGON

这些技术不是名单，而是一条从数据到画面的链

以“模型又返回了一句话”为例：网络事件到达 → 同步层更新消息数据 → 界面库知道哪部分数据变了 → 更新浏览器中的文字节点 → CSS 让它按主题与布局显示。下面的每个词都在这条链上有具体位置。

响应式：你修改数据，相关画面跟着变化

假设一个按钮显示“连接中 / 已连接”。传统手工做法是每次状态变化都找到按钮并改文字。响应式做法是声明“按钮文字依赖连接状态”，状态改变后自动更新依赖它的那一处。Solid 的 signal 是这类状态的基本形式，store 适合更复杂的数据。

const [status, setStatus] = createSignal("连接中")
// 页面读取 status()，建立依赖
// 网络确认连接后，setStatus("已连接")
// 依赖它的文字更新，不必刷新整个网页。

组件是把一块界面和相关逻辑组织在一起的函数/单元。Provider 与 Context 则让一组组件取得同一套服务，例如主题、连接与同步状态，避免每层手动传递所有参数。oco 挂载 AppBaseProviders 和 AppInterface，就是尽量沿用官方 App 所需的运行上下文。

类型检查为什么不能替代运行时校验？

TypeScript 可以检查开发者写的 sessionId 是否按预期作为字符串使用，但来自网页消息、网络或旧版本的数据仍可能错误。类型信息不会在运行时自动变成一道门禁。因此公共契约既定义类型，也有实际解析和校验函数；桥还要继续检查 generation、目录与会话范围。

Node.js 与浏览器都运行 JS，但能做的事不同

浏览器有 DOM、页面事件、Fetch 和 Worker；Node.js 宿主有进程、文件系统和 VS Code 提供的扩展 API。不能在网页里直接使用 vscode.workspace，也不能在宿主里直接操作网页 DOM。消息桥正是这两种环境之间的接口。

Worker：把耗时工作挪出页面主执行线

代码语法高亮可能处理大量文本。Worker 让这类工作在另一条执行线上运行，减少阻塞输入与滚动。Webview 对 Worker 资源加载有约束，oco 将脚本打成自包含 IIFE，用 blob 引导，并为额外语言资源设置受限获取路径。IIFE 在这里可以理解为“加载后自行运行的一整份脚本”，不是新框架。

主题适配则把 VS Code 的外观信息传给嵌入页面。语言也是另一条独立链路：扩展原生命令当前使用英文，官方聊天与轨迹按 OpenCode 语言设置工作；不能从侧栏语言推断模型会用什么语言思考或输出。

怎样解读状态标签？

  • PASS：这一次命令或用例实际执行并通过，需附版本与环境。
  • FAIL：实际执行但不满足断言，需要判断产品缺陷还是测试环境/时序问题。
  • NOT RUN：这次没有运行，不能从历史记录补成通过。
  • BLOCKED：环境或前提不足，例如真实模型不可用；不是通过，也不等于已证明产品有错。
  • MIXED_REVISIONS：证据来自多个提交，不能拼成某个当前版本的完整通过。

稳定交付最好形成一条可追溯链：提交/dirty 状态 → 检查结果 → 产物哈希 → 安装位置 → 重载后的用户操作。这样“昨晚跑过”和“你明早实际用的版本”才有可能是同一个东西。

依据：测试分层 · 验收矩阵（含旧状态措辞） · 实际套件列表 · 证据分类 · 离线检查执行

14 · RISK REGISTER

风险不只列名字，要讲触发条件和验证方法

以下是架构和当前证据对应的风险，不是“已经发现了所有这些故障”。P0 表示一旦出问题会造成安全、任务语义或交付可信度的严重影响；P1 表示需重点关注体验、稳定性或维护成本。这里的级别是本手册的评估，不替代项目任务编号。

显示全部风险

R01 · 网页请求越权，或凭据被带到错误服务 P0

何时发生：前端消息被篡改、服务地址变化、权限回复被错误配给另一个会话。

当前防线：虚拟源限制、运行时消息校验、generation、目录固定、业务写入会话校验、宿主持有凭据、手动处理重定向、CSP。

剩余边界：读请求的策略比写更宽；CSP 不是完整沙箱证明，TypeScript 也不是运行时授权。应回归伪造消息、旧代响应、跨目录/跨会话写与凭据隔离。

R02 · “停止”只断了网络，任务却继续运行 P0

何时发生：把关面板、流取消或排队发送取消误当成停止执行。

当前防线：网络 Abort 与服务执行生命周期分开，关闭面板明确不停止服务器任务。

验证：在隔离测试会话发起足够长的真实运行，点击业务停止，核对服务端状态和后续工具是否停止；mock 与 HTTP abort 不能代替该证据。

R03 · 重连或超时造成重复发送、串会话 P0

何时发生：请求已被服务接受但响应丢失；快速切换后旧响应或草稿迟到。

当前防线：面板绑定、文档换代、草稿确认、宿主导航、侧栏先缓冲再快照。

剩余边界：没有端到端事件游标就不能保证任意断网窗口都无遗漏；有副作用请求不能盲目重发。应验证发送中断网、切换、重载、恢复后实际消息数量。

R04 · 远程路径对应错机器，或文件越界 P0

何时发生：服务器路径被当作本机路径，或符号链接/相对路径逃出工作区。

当前防线：回环服务前提、真实路径和工作区包含关系、普通文件检查。

剩余边界：本机回环端口也可能是 SSH 转发，地址本身不能完全证明文件系统同源。跨机附件应验证字节、来源和 MIME；不能只看缩略图或路径字符串。

R05 · 进程清理误伤用户已有 OpenCode P0

何时发生：把已存在端口或 attached 服务当成扩展自己的子进程。

当前防线：managed 只追踪自己 spawn 的对象；attached 只连接；配置与工作区信任限制。

验证：关闭面板、停用扩展、切换工作区后，外部服务应仍存活；managed 则应只清理自己的进程。异常退出不应重启风暴。

R06 · 把不同版本的证据拼成“可以交付” P0

何时发生：多个会话并发编辑、构建含 dirty 改动、只验证宿主包没验证网页资源、部署后未重载。

当前防线：提交与哈希记录、brief 的版本分类、明确 NOT RUN/BLOCKED。

验收门槛：最终候选版本、相关检查、实际包和目标环境必须对应；用户宣称可用的关键链路要有真实证据。

R07 · 上游内部接口与补丁升级耦合 P1

何时发生：升级 App、SDK、路由、组件结构或 Server，旧补丁不再适配。

当前防线：固定 tag/SHA，补丁集中记录，可重放。

剩余工作：除了 apply 成功，还需检查实际修改语义、嵌入入口、快捷键、路由、设置与核心聊天回归。不能自动跟随上游最新版本。

R08 · Webview 资源限制导致白屏、Worker 或链接异常 P1

何时发生：跨源 SVG、Worker 动态加载、模块相对路径、CSP 或普通网页跳转碰到 VS Code 特殊资源源。

当前防线：sprite 内联、自包含 Worker 与语言资源白名单、宿主导航、特定上游补丁。

验证：首开与重载、罕见语言代码块、文件/子会话链接、离线失败恢复；不能只看浏览器开发服务器正常。

R09 · 常驻面板、多条事件流与无完整背压 P1

何时发生：多个固定面板、长会话、高频工具输出、慢远程连接、数小时使用。

当前防线：主面板复用、部分请求合并和清理生命周期。

未完成边界：并非跨面板共享 SSE；端到端背压未实现，面板上限/LRU 未建立。需要测量长期内存与连接数量，不应只测一次切换耗时。

R10 · 首屏优化依赖构建产物形状 P1

何时发生：Vite 输出格式、模块路径或浏览器解压能力变化，gzip/import map 加载器不再适用。

当前防线：原入口回退、首屏请求排序、骨架屏与超时释放。

验证：必须检查冷开、慢网、回退路径、动态 import、Worker；遮住闪屏改善外观，不等于服务响应本身更快。

R11 · 图片、中文输入法、键盘与主题仍有真实环境差异 P1

何时发生：真实系统剪贴板、组合输入、焦点切换、窄面板、高对比度或 Windows。

当前防线：已有部分适配与自动化用例，相关历史记录可追溯。

证据限制：合成 composition 事件不等于真人 IME；自动注入图片不等于系统粘贴。应以目标机器的实际操作补齐，不把它们从自动化通过数中推导出来。

R12 · 文档与发布身份漂移 P1

何时发生：旧计划仍写 Agents、旧补丁数和测试数，或把本地测试 VSIX 当正式版本。

当前防线：STATUS/NEXT 为唯一现状/队列，手册区分历史与实现。

交付要求：清楚说明支持范围、安装与回退路径、正式 publisher 与自身许可证的待决定项；保留上游许可证，不把用户期待变成未经验证的兼容承诺。

风险来自上述实际机制与 源码审计、构建/文档审计。已知待验证项与后续队列以 STATUS、NEXT 为准。

建议的四次阅读练习

  3. 追一次切换：从侧栏选会话到 panels 的 main/pinned，再到 navigate、ready、草稿投递。
  4. 追一个已有修复：例如子会话外开浏览器，先读 evidence，再看 0016 补丁与回归测试，理解为什么单改样式解决不了问题。

“Webview 不就是 iframe 吗？”

VS Code 官方会用 iframe 类比 Webview，VS Code 的内部实现也可能包含 frame。本文区分的是应用的集成方式：oco 并未只是往一个 iframe 的 src 填上远端 OpenCode 网站网址；它将官方 App 源码编译为自己的扩展资源，在受控 Webview 内运行。这与 VS Code 底层是否使用 frame 不矛盾。

“前端包已固定，为何服务版本还要检查？”

前端负责理解响应字段和发出预期请求，服务负责实现接口。固定前端只是固定了协议的一端；如果服务版本或企业分支改变字段、权限、事件语义，仍可能出现不兼容。消息桥改变了运输路径，没有自动解决业务协议差异。

“为什么这份手册自己没用 Solid？”

这是独立、可离线阅读的技术文档，不是 oco 产品界面。少量原生 JavaScript 足以支持目录搜索、流程教学和筛选，无需给阅读增加包管理器、构建步骤或网络依赖。
